01 · Problem & Gap

Tool wear is invisible until it isn't.

The Problem

Wear happens where no one can see it.

Flank wear develops at the tool tip, inside the cut, under coolant — an operator cannot see it, and by the time a part shows a defect, the tool has already produced scrap. So most shops fall back on fixed-schedule tool changes: swap every N parts, or every shift, whether the tool needs it or not.

Why It Matters

A schedule is always wrong in one direction.

Change too early and a shop discards carbide inserts with real cutting life left, inflating tooling spend across hundreds of changes a month. Change too late and a degrading tool drifts out of tolerance, scraps the workpiece, or — at spindle speed — fractures, which is a genuine hazard to the operator standing at the machine, not just a cost.

The Data Already Exists

It's discarded, not interpreted.

Spindle speed, torque, temperature and cumulative runtime already stream off CNC machines during every cut. The gap isn't sensing — it's turning that stream into a number an operator can act on, and trust.

02 · The Innovation

Two questions, kept deliberately separate.

Metrik treats "will this cut scrap the part?" and "how worn is this insert right now?" as two different questions — because only one of them can be honestly answered from a synthetic benchmark, and conflating them is how monitoring tools end up quoting a number they can't actually support. Keeping them separate, and being explicit about which is which, is itself part of the innovation.

01

Physics-Grounded, Not Black-Box

Every wear estimate is checked against Taylor's tool-life equation (V·Tn=C, 1907) — the standard the machining industry already trusts — instead of asking an operator to accept a machine-learning number on faith alone.

02

Validation Methodology as a Feature

The wear model is validated leave-one-tool-out — tested on a cutter it never trained on. Measured on the same data, a naive random split reports a 10.7× more optimistic error, and that gap is reported, not hidden.

03

Explainable Per Prediction

SHAP decomposes every single prediction into a ranked list of which parameter is driving it — torque, runtime, temperature — so an operator knows what to correct, not just that something is wrong.

04

A Closed Human Feedback Loop

Every operator verdict on a tool change is logged and scored against what the model predicted, surfaced with a Wilson-score confidence interval — and honestly caveated as a field sanity check, not a validation metric, because it's a biased sample.

"The defensible claim is not 'better than any schedule' — it's 'removes the need to guess the schedule.'"

03 · How It Works

From spindle telemetry to a tool-change decision.

INPUT

Spindle Telemetry

  • Speed, torque, temperature, runtime
  • 3-axis force / vibration / acoustic emission
  • Live sensor feed, CSV upload, or simulator
PROCESSING

Feature Engineering

  • Baseline-relative windowing vs. fresh-tool signature
  • Cumulative exposure & smoothed trend
  • Missing-sensor fallback / derivation
INTELLIGENCE

Dual Model + Physics

  • XGBoost flank-wear regressor
  • XGBoost scrap-risk classifier (calibrated)
  • Taylor life baseline + SHAP explainer
OUTPUT

Decision-Ready Estimate

  • Wear % and risk % with confidence band
  • Remaining life in minutes

USER / ACTION

Operator Decides

  • Fleet dashboard, per-machine detail
  • Acknowledge or log a tool change
  • Verdict feeds the accuracy scoreboard

Never actuates the machine

Every endpoint in the system is read-and-recommend. Metrik does not stop, throttle, or reconfigure a machine — a person always makes the final call, and that call is what closes the feedback loop.

One feature pipeline, two callers

The exact same feature-extraction code runs at training time and at inference time, so a live machine can never drift out of sync with how the model was actually trained — a common, quiet failure mode this design rules out by construction.

Persistent, multi-tenant fleet state

Every account's machines, tool-change history, and running scrap-saved total are mirrored to SQLite, so a server restart doesn't erase a plant's history. Two accounts never see each other's fleet.

Graceful under an incomplete sensor package

A real shop's machines don't all report the same fields. Missing readings fall back to a training-median or are derived from related sensors — the system is designed to never crash on an incomplete payload.

Feature engineering

Seven condition-monitoring channels (3-axis force, 3-axis vibration, acoustic emission) are windowed every 2 seconds and expressed relative to a fresh-tool baseline captured in the first ~30 seconds after each tool change — because absolute force levels depend on the fixture and machine, not just the wear.

API surface

Auth (register/login/session) · Fleet (machine list, detail, add/remove, state) · Predict (live & What-If simulator, CSV batch) · Human-in-the-loop (tool-change log, acknowledge, feedback scoreboard) · Chat · Export (JSON/PDF) — every fleet route scoped to the logged-in account.

Robustness by design

CSV uploads are capped in size and row count against resource exhaustion; every sensor field has a documented fallback; the frontend badges any value the backend had to estimate rather than presenting it as measured.

Calibration, not just accuracy

The risk classifier's raw score is corrected with Platt scaling so a "70%" actually means observed at ~70% frequency — cutting the calibration error (Brier score) by 32%, without changing which machines alarm.

10.7×
optimism gap

The single most common error in tool-wear research is validating on a random row split — consecutive readings from the same cutter are nearly identical, so a model can memorize one tool's own wear curve. Measured on Metrik's exact data, that invalid split reports 1.5 µm MAE (R² 0.995) — a result 10.7× more optimistic than the honest, leave-one-tool-out number of 16.0 µm. Both numbers are computed and reported every training run, on purpose.

Tool life recovered vs. a fixed schedule

Across the three validated cutters, a practical fixed schedule (built with an 80% safety margin) uses 74.1% of available tool life before changing it; Metrik's condition-based estimate uses 88.5% — +19.3% more usable life recovered, and −4.6% against an oracle schedule that would need foreknowledge no real shop has. Zero tools were changed late under either policy.

Honest limitation: cross-material transfer

Trained on steel and tested zero-shot on titanium cutters it never saw, wear-magnitude accuracy degrades from 16.0 µm to 38 µm MAE. Per-machine baselining is what makes deployment on an unseen machine viable at all — but the gap is measured and reported, not smoothed over.

All figures above are offline validation results on published research datasets (PHM 2010 Data Challenge; AI4I 2020 / Kaggle). The demo fleet replays these real, physically measured cutting signals rather than synthesizing them. The system has not yet been field-validated at a live production shop.

06 · Features & Impact

From a model to a shop-floor decision.

Live Fleet Dashboard

Per-machine wear/risk gauges, live sensor readout, and a fleet-wide KPI view polling continuously.

What-If Simulator

Move spindle speed, torque, depth-of-cut or runtime and watch the risk gauge and SHAP drivers respond live.

SHAP Driver View

Every prediction ships with a ranked breakdown of which sensor reading is actually driving the number.

CSV Batch Prediction

Upload a spreadsheet of readings and get a wear/risk verdict per row — no pre-loaded numbers, real model response.

Tool-Change Workflow

An operator logs whether a tool was genuinely worn when changed — a labelled event that closes the ML loop.

Model Feedback Scoreboard

Aggregates operator verdicts into a live accuracy read, with a statistically honest confidence interval.

Conversational Assistant

Ask about a machine's status in plain language; answered by a hosted LLM grounded in that machine's live data.

Multi-Tenant Accounts

Every plant's machines, history and scrap-saved total are scoped to its own account and persist across restarts.

Who Benefits

Operators get a live, explained wear reading at the machine instead of a guess from a calendar. Plant managers get the fleet-wide view — which machines are at risk now, and evidence to plan maintenance windows around production.

What It Reduces

Waste in both directions: parts scrapped by an undetected worn tool, and tools discarded early with usable carbide life still in them — the two costs a fixed schedule can never simultaneously avoid.

Why It Scales Down-Market

Built on standard telemetry — speed, torque, temperature, runtime — rather than proprietary sensor hardware, so small and mid-sized job shops can adopt it without a vendor monitoring-suite budget.

07 · Differentiation & What's Next

Where this stands, and where it goes.

Why It Stands Out
  • Grounds machine learning against a trusted physics equation instead of shipping a pure black box.
  • Reports its own validation-leakage gap (10.7×) rather than quoting the flattering number.
  • Explains every prediction with SHAP; never hands over a score with no reason attached.
  • Closes the loop with real operator verdicts, honestly caveated for sampling bias.
Current Implementation Working prototype
  • Full-stack app: FastAPI backend, React dashboard, SQLite persistence, multi-tenant auth.
  • Both models trained, calibrated, and leave-one-tool-out / cross-validated with reported metrics.
  • CSV batch prediction, What-If simulator, tool-change workflow, and feedback scoreboard all working end-to-end.
Current Prototype Scope Honest limits
  • Demo telemetry replays real recorded PHM 2010 signals; not yet wired to a live shop-floor sensor feed.
  • The risk classifier trains on a synthetic benchmark, not field failure data — stated plainly, not hidden.
  • Not yet pilot-tested with an external shop; no field deployment exists today.
Future Potential Next steps
  • Live sensor / PLC integration with a partner machine shop for a real pilot.
  • Extend wear-model generalization across work materials beyond steel.
  • Mobile / edge-side inference for shop floors without a fixed workstation.

Metrik doesn't ask a shop to trust a black box — it grounds a machine-learning wear estimate in the physics the industry already trusts, explains every number it shows, and reports its own validation honestly enough to survive scrutiny. That combination, not any single model, is the innovation.
