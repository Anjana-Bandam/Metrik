# Metrik

**AI-Powered CNC Predictive Maintenance for Zero Scrap.**

Metrik predicts CNC tool-wear probability from live spindle telemetry,
explains *why* with SHAP, estimates time-to-failure and scrap cost, and lets
an operator plan safe cutting parameters before a job starts. It is
**decision support only** — nothing in this app stops, throttles, or
reconfigures a machine. Every recommendation carries a confidence
percentage and is reviewed by a person.

## 1. Backend setup

```bash
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

# Train the model (reads data/predictive_maintenance.csv, writes .pkl + .json
# artifacts into models/). The CSV is already included in this folder.
python models/train_model.py        # scrap-risk model + calibration
python models/train_wear_model.py   # flank-wear model (real measured data)

# Start the API
uvicorn api.main:app --reload --port 8000
```

The API is now live at `http://127.0.0.1:8000`. Interactive docs at
`http://127.0.0.1:8000/docs`.

If you ever want to watch raw simulated sensor JSON print to your terminal
independently of the API:

```bash
python utils/live_machine_simulator.py
```

## 2. Frontend setup

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. Vite proxies all `/api/*` calls to the FastAPI
backend on port 8000 (see `vite.config.js`) — no CORS/URL setup needed.

## 3. What you'll see

- **Dashboard** — 4 KPI cards (active machines, active warnings, avg.
  remaining life, scrap saved) and a live grid of 5 machine cards, polling
  the backend every 2 seconds. Click any card for the full detail view:
  side-by-side tool-wear and scrap-risk gauges, a SHAP driver chart,
  live sensor readout, and
  the AI narrative box with a one-click JSON export.
- **Simulation** — the What-If sandbox. Move the Spindle Speed, Spindle Torque,
  Depth of Cut, or Runtime sliders and the risk gauge + SHAP chart update
  live by calling `/predict`. Nothing here touches a real machine.
- **Reports** — export any single machine's full prediction record, or the
  whole fleet's status, as JSON.
- **Settings** — Dark / Light / System theme toggle and a short "how this
  works" note.

## Data & modeling notes

Metrik runs **two** models, because "will this cut scrap the part?" and "how
worn is this insert?" are different questions, and only one of them can be
answered from a synthetic benchmark. Keeping them separate is deliberate: it
is what stops one model's numbers being quoted for the other's question.

| | Scrap-risk model | Flank-wear model |
|---|---|---|
| Question | Probability the current cut ends in a wear-driven scrap event | Flank wear right now, in mm |
| Data | AI4I 2020 (synthetic benchmark) | PHM 2010 milling challenge (**real**, physically measured wear) |
| Output | Probability 0–100% | Millimetres, against the ISO 8688 0.30 mm limit |
| Validation | 5×10 repeated stratified CV | **Leave-one-tool-out** |
| Headline | PR-AUC 0.702, precision 69% / recall 61% | MAE **16.0 µm**, R² **0.724** |
| Output units | Calibrated probability (Brier 0.0084 → **0.0057**) | Millimetres of flank wear |
| Script | `models/train_model.py` | `models/train_wear_model.py` |

### Flank-wear model (the tool-wear claim)

- Source: PHM 2010 Data Challenge, via the Katulu `uniwear` bundle (CC BY 4.0)
  — `backend/data/phm2010_tool_wear.csv`. Three tungsten-carbide cutters
  machining HRC52 stainless steel, run to end of life, with flank wear
  physically measured after every cut. Seven condition-monitoring channels:
  3-axis cutting force, 3-axis vibration, acoustic emission.
- **Validation is leave-one-tool-out**, i.e. train on two cutters and predict a
  third the model has never seen. This matters more than any hyperparameter:
  consecutive windows from one cutter are nearly identical, so a random row
  split lets the model memorise each tool's own wear curve. Measured on this
  exact data, a random split reports **1.5 µm MAE (R² 0.995)** against the
  honest **16.0 µm (R² 0.724)** — a **10.7× optimism gap**. The training script
  prints both numbers every run, on purpose.
- Features are expressed **relative to a fresh-tool baseline** captured in the
  first ~30 s after each tool change, plus cumulative mechanical exposure and
  smoothed trend. Absolute force levels depend on fixture and machine, so a
  model trained on them learns the setup rather than the wear.
- Honest limitation, measured and reported: wear magnitude does **not** transfer
  across workpiece materials. Trained on steel and tested zero-shot on nine
  titanium cutters, MAE degrades to 38 µm. Per-machine baselining is what makes
  deployment on an unseen machine viable.
- **Remaining useful life (RUL)** is projected by least-squares fit on the
  tool's own recent wear trend, refusing to quote a figure when the trend is
  not statistically distinguishable from flat (this guard is the difference
  between a median error of ~8 min and a *mean* error of over two hours).
  Validated at 1,420 points across the three cutters: median absolute error
  **464 s**, and — the number that matters — **20 s in the final quarter of
  tool life**, which is when the answer is actually needed.
- **Versus a fixed tool-change schedule** (the honest, mixed result):

  | Policy | Mean tool life used |
  |---|---|
  | Oracle fixed schedule (needs perfect foreknowledge) | 92.7% |
  | Practical fixed schedule (80% safety margin) | 74.1% |
  | Metrik, condition-based | **88.5%** |

  Metrik recovers **+19.3%** tool life against the schedule a shop can actually
  set, and **−4.6%** against an oracle schedule it cannot. Zero tools changed
  late in either case. The negative half is reported deliberately: these three
  cutters differ in usable life by only 13%, so one fixed interval already fits
  them all. Condition monitoring pays off when tool lives *vary*, and three
  cutters on one workpiece in one machine is close to the worst case for
  showing that. The defensible claim is not "better than any schedule" but
  "removes the need to guess the schedule".
- The demo fleet has no dynamometer, so it **replays the real measured signals**
  from these cutters rather than synthesising plausible-looking traces. A
  production install feeds live sensors through the identical code path
  (`utils/wear_features.py`).

### Scrap-risk model

- **Calibrated.** `scale_pos_weight` is needed to train under 1.2% prevalence
  but it distorts the output: raw scores of 70–90% corresponded to a ~14%
  observed failure rate. Platt scaling on 100,000 pooled out-of-fold
  predictions maps the score back onto observed frequency (Brier 0.0084 →
  0.0057, a 32% improvement). The mapping is monotonic, so ROC-AUC and PR-AUC
  are unchanged — only the number's *meaning* changes. Alert bands
  (watch ≥15.6%, act ≥27.7%) are the same operating points as the old raw
  0.40/0.70 cut-offs, so the same machines alarm at the same moments.

- Source dataset: Kaggle "Machine Predictive Maintenance Classification"
  (`backend/data/predictive_maintenance.csv`, included). This dataset is
  **synthetic**, generated from published rules, and its tool-wear failures are
  drawn at a random point in a 200–240 min window — so tool wear alone is not
  predictable from it beyond a ~5% precision ceiling, no matter the model. That
  measured limitation is why the flank-wear model above exists.
- Columns renamed to CNC terminology: `Rotational speed [rpm]` → `Spindle
  Speed [rpm]`, `Torque [Nm]` → `Spindle Torque [Nm]` (torque is used as the
  mechanical-load signal), `Tool wear [min]` → `Cumulative Tool Runtime [min]`.
  Note this column is **torque in Nm**, not a feed rate — an earlier build
  mislabelled it `Feed Rate [Nm]`, which contradicted its own unit. Machines
  saved under the old name migrate automatically on load.
- Engineered feature: `Material Hardness Index` (L=1, M=2, H=3) from `Type`.
- Model: XGBoost classifier on `StandardScaler`-scaled features, with
  `scale_pos_weight` set to correct for class imbalance. The label is
  `Tool Wear Failure OR Overstrain Failure` (~1.2% positive rate), not the
  raw dataset's generic `Target` column — Overstrain is included because
  this dataset's own generation rule defines it as `tool_wear × torque >
  threshold`, i.e. mechanically wear-driven, matching this project's scope
  (see `backend/models/train_model.py` for the full rationale). Three
  physics-interaction features are engineered from the same raw sensor
  readings (no new attribute): `Wear x Load`, `Temp Diff [K]`, and
  `Est Power [W]` — giving the model the exact `wear × torque` interaction
  the Overstrain rule is built on, instead of making it approximate that
  interaction with splits. Validated via 5-fold × 10-repeat stratified
  cross-validation (50 fits, 100,000 pooled predictions): ROC-AUC 0.983,
  PR-AUC 0.702 (vs. a 0.012 random baseline); precision 69% / recall 61%
  at the app's 70% red-alert threshold. Outputs a probability (0–100%),
  never a hard 0/1.
- Explainability: SHAP `TreeExplainer` on every prediction, surfaced as a
  ranked, normalized contribution-percentage list.
- **Sensor flexibility**: `backend/utils/sensor_config.py` defines a
  fallback per feature — missing readings fall back to the training median,
  or (for Spindle Torque specifically) are estimated from Spindle Speed and
  Runtime. The app never crashes on an incomplete sensor payload; the UI
  marks estimated fields with a small info badge.
- Cost impact is a mock formula for the demo: `risk% × $150 / 100`.
- The chatbot narrative is fully mocked with deterministic Python logic
  (no API key, no network call) — swap `chatbot_mock.py` for a real Azure
  OpenAI call later without changing its return shape.

## Design notes

Dark mode by default (with Light/System toggle), glassmorphism cards,
Poppins for display type, Inter for body text, and JetBrains Mono for every
numeric telemetry readout so sensor values read like an instrument panel.
The signature mark is a machined dial/gauge motif that recurs in the logo,
the risk gauges, and the range-slider thumbs.
